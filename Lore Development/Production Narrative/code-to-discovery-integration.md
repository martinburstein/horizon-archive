# Code-to-Discovery Integration

This document maps real learning actions to narrative consequences. Python remains valid Python; Azure and Foundry lessons remain source-grounded in curriculum content. Lore supplies motive, data, and visible response.

Every fictional task also follows the [Builder landscape function and reveal contract](builder-landscape-function-and-reveal-contract.md). A safe exercise may reveal one input, transformation, output, or stewardship relation. It must not convert a provisional Pilot occupation into native Builder purpose or imply that human software is technological parity.

## Core contract

Each exercise has five fields:

1. `learning_goal`: the exact skill or AI-901 objective.
2. `fictional_task`: why the pilot needs the operation now.
3. `valid_solution_space`: accepted real syntax or defensible scenario choices.
4. `world_response`: visible, audible, or structural change after success.
5. `evidence_payload`: the bounded lore fact unlocked, including provenance tag.

If an exercise cannot provide both a world response and an evidence payload, it is probably detached from the adventure.

## Python progression patterns

| Skill | Fictional operation | Discovery consequence | Guardrail |
|---|---|---|---|
| Run a file / `print()` | Send one visible bounded request through the Pilot's mediation layer | The local surface repeats a measurable result | Do not imply Python is native Builder language or the surface was designed for a human |
| Strings | Label a signal, inscription, or hypothesis | The archive distinguishes the player's label from its own term | Player-authored names must not become Builder canon |
| Variables | Preserve call sign, reading, or working interpretation | The site can refer back to a value the player supplied | Make provenance visible |
| Numbers | Record interval, count, confidence, coordinate, or frequency | A pattern becomes measurable rather than merely uncanny | Avoid arbitrary combination-lock math |
| Booleans | Represent a narrow detected/not-detected state | Paired Builder states reveal distinctions | Never reduce consciousness or life to one Boolean |
| Tracebacks | Repair a malformed request | Stable retry behavior demonstrates repeatable mediation | No narrative punishment for mistakes or claim of Machine patience |
| Lists | Gather fragments or repeated signals | Scope expands from one artifact to a collection | Preserve order only when evidence supports it |
| Dictionaries | Model a record with value plus provenance | Identity and evidence categories become separable | Do not create a canonical `soul` key |
| Conditionals | Route evidence by explicit criteria | Different records receive different handling | Show the cost of a weak criterion safely |
| Loops | Scan many fragments or sites | Recurrence becomes visible at civilizational scale | Avoid grinding; keep collections small enough to inspect |
| Functions | Reuse a comparison, parsing, or validation operation | The same protocol works across unlike surfaces | Similar response does not prove common consciousness |
| Files | Open logs, images, audio, and saved reports | The archive becomes tangible and revisitable | Distinguish source files from generated outputs |
| JSON | Inspect nested event and witness records | Contradictions can coexist structurally | Null and missing must not be silently conflated |
| Environment variables | Keep access material out of code | Old boundaries around sensitive records gain meaning | Never expose real secrets in samples |
| Requests/responses | Contact a distant local surface | The terminal is revealed as one endpoint in a network | Response does not automatically mean present agency |

## AI and Azure workload patterns

### Workload selection

Give the player an evidence problem first: an inscription, damaged voice, image sequence, or mixed-media memorial. Ask which capability fits the evidence. Correct selection changes what can be observed; it should not simply award a quiz checkmark.

### Responsible AI

Use Builder records as the subject only when the exercise clearly distinguishes respectful fictional archaeology from claims about real cultures. Strong scenarios include privacy after absence, provenance, accessibility, uncertainty, and the difference between technical capability and permission.

### Generative AI

Use generation for translation hypotheses, missing-architecture visualization, alternative summaries, and simulated counterexamples. Generated material must be visibly labeled and toggleable against sources. A generated output may suggest where to look next but cannot itself confirm lore.

### Foundry model/deployment choices

Frame model choice around task fit, modality, cost/latency constraints, and evaluation. Narrative variants should alter the form or breadth of the result, not lock the player into irreversible story branches based on vendor trivia.

### Endpoints and SDKs

The Pilot's local software is the client; Builder surfaces are fictional data sources behind a translation/mediation layer. Keep actual SDK concepts and examples faithful to the curriculum's official sources. Never present fictional Builder protocol as Microsoft product behavior.

### Agents

The Pilot's local agent may search approved sources, compare records, call bounded tools, and draft a report. It may not autonomously activate unknown infrastructure, infer private attributes, delete contradictory evidence, or declare the central mystery solved. The Pilot reviews the trace and authorizes any consequential next step.

### Content Understanding

Use mixed Builder artifacts as the fictional corpus: slabs, diagrams, field recordings, environmental telemetry, and memorial records. The output schema should include source location, modality, extracted fields, confidence/uncertainty, and contradictions. The exercise teaches structure while the unexpected shape of the data advances the mystery.

## Exercise blueprints

### Blueprint A: first visible output

- Learning goal: PY-001 through PY-003.
- Fictional task: test one exposed input relation with a diagnostic phrase.
- World response: one physical component activates and returns the exact output.
- Evidence payload: the surface was monitoring an input channel before activation.
- Ambiguity: no claim about who monitored it or why the phrase was accepted.

### Blueprint B: provenance dictionary

- Learning goal: PY-009, PY-016, PY-020.
- Fictional task: encode an observation with source, time, interpretation, and confidence.
- World response: a memorial face opens only when observation and inference are separate fields.
- Evidence payload: Builder archives structurally preserved epistemic distinctions.
- Ambiguity: no claim that the translated field names have exact human equivalents.

### Blueprint C: loop across witness fragments

- Learning goal: PY-011.
- Fictional task: scan a short list of records for a recurring designation.
- World response: matching architectural markers light in different parts of the scene.
- Evidence payload: the designation spans multiple eras or embodiments.
- Ambiguity: designation match is not proof of continuous subjecthood.

### Blueprint D: safe agent trace review

- Learning goal: AI901-D2-O4 plus grounded prompting.
- Fictional task: ask the expedition agent to assemble evidence from three sites.
- World response: the network map gains evidence links, each traceable to a source.
- Evidence payload: distant sites share a structured condition.
- Required player act: reject or relabel one unsupported agent conclusion.
- Ambiguity: coordination is confirmed; consciousness and motive are not.

### Blueprint E: multimodal extraction

- Learning goal: AI901-D2-O7.
- Fictional task: extract aligned fields from an image, transcript, and sensor log.
- World response: a missing interval appears in all three modalities.
- Evidence payload: omission was coordinated across record types.
- Ambiguity: purpose of the omission remains unknown.

### Blueprint F: capstone horizon report

- Learning goal: L-06-03 readiness synthesis.
- Fictional task: create a report with observations, correlations, inferences, hypotheses, unknowns, and next safe action.
- World response: distributed surfaces accept the report and expose a reversible route.
- Evidence payload: structured uncertainty is operationally meaningful to the network.
- Ambiguity: acceptance is not proof of approval, judgment, or mind.

## Mastery and narrative access

- Core story progress requires demonstrated understanding but always permits hints and retry.
- Hint use may trigger optional remediation, never a lesser story outcome.
- Optional lore can reward deeper mastery, but central emotional beats must remain accessible.
- Wrong answers may reveal interface behavior, but should not contain unique canon that careful learners miss.
- Repeated failure should shift the fiction from "test" to "calibration" and offer a smaller safe step.
- The player's final report should reflect which evidence they inspected, while all versions preserve the same surface-canon unknowns.

## Content validation checklist

Before shipping an exercise, verify:

- The shown Python parses and runs as real Python where execution is claimed.
- Accepted variants are broader than one whitespace-perfect answer when the language permits it.
- Microsoft product claims are sourced in the curriculum layer, not invented by the lore layer.
- The unlocked statement has an evidence tag.
- A generated hypothesis is never presented as an observation.
- The exercise changes the scene or the player's available understanding.
- Failure is recoverable and does not erase story access.
- The central mystery remains larger after the discovery, not merely postponed by withholding text.
